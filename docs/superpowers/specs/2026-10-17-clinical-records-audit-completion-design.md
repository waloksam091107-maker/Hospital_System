# 病历草稿、审计查询与审计完整性补全设计

## 目标与范围

在不更换现有 Servlet、MyBatis、MySQL、Tomcat 架构的前提下，补齐已确认的三项差距：医生保存和恢复病历草稿、完成接诊的必填规则；管理员按条件查询审计日志；关键操作的审计完整性。继续保留现有预约、排班、登录和已完成病历数据，不重建数据库或覆盖部署环境。

此前已通过的人工测试是回归基线，不代表本次新增功能已验收。实现后必须分别验证功能、权限、事务和故障处理。

## 当前代码依据

- `database/migrations/20261014_medical_records_and_orders.sql` 定义 `medical_records`、`medical_orders`；病历按预约唯一，`diagnosis` 非空，`treatment_plan` 可空，没有草稿状态。
- `MedicalRecordsServiceImpl.finalizeEncounter` 将病历、医嘱和预约完成状态放在一个事务里，但只强制填写诊断；`MedicalRecordsServlet` 没有保存草稿接口。
- `MedicalRecordsMapper.xml` 的患者查询按患者归属筛选，但尚未按病历状态筛选；新增草稿后必须让患者查询只返回正式病历。
- `AuditFilter` 在请求结束后调用 `AuditService` 独立写日志，日志失败会被吞掉；不能保证业务成功必有审计。它只能从部分请求参数识别目标，新增预约等日志可能没有目标编号。
- `AuditLogsServlet`、`AuditLogsMapper.xml` 和 `hospro/audit-logs.html` 目前提供最近记录，尚不支持条件查询；读取异常被转换为空列表，无法区别故障和无结果。

## 一、病历草稿与完成接诊

### 数据与状态

扩展现有 `medical_records`，保留预约唯一约束、原字段及现有数据：

- `record_status`：`DRAFT` 或 `FINAL`；迁移前已存在的病历视为 `FINAL`。不推测或伪造历史提交时间。
- `finalized_at`：正式提交时间；历史记录无法确认实际完成时间时保留 `NULL`。
- `version`：非负版本号，草稿每次成功保存递增，用于检测两个窗口并发编辑；首次创建时使用明确的初始版本。
- `diagnosis` 改为允许 `NULL`，使未填写诊断的草稿可保存。完成接诊时在服务端要求诊断和 `treatment_plan` 均为非空白，并保持现有长度约束。`medical_advice` 和医嘱项目保持可选；已填写的医嘱仍需满足现有格式、数量及长度规则。

服务端从 Session 取得医生身份，并锁定预约、按需锁定对应病历。仅本人 `IN_PROGRESS` 预约允许创建或更新草稿；保存草稿时预约保持 `IN_PROGRESS`。患者的列表、详情及医嘱查询只能访问本人 `FINAL` 病历，不能通过变更编号读取草稿或其他患者的数据。

医生可在没有草稿时直接完成接诊，也可提交已有草稿：锁定并核对预约归属、状态与草稿版本，验证必填内容，保存病历及医嘱，将病历设为 `FINAL`，记录提交时间，将预约设为 `COMPLETED`，并写入成功审计；上述操作在同一个数据库事务中全部提交或全部回滚。若不存在草稿，以插入一份 `FINAL` 病历的方式完成；已有 `FINAL` 病历不可被普通医生静默覆盖。

预约唯一约束、行锁及版本校验共同处理首次创建、提交与多窗口竞争。旧版本提交返回 409 和可理解的提示，页面保留尚未提交的输入，供医生重新读取或自行复制；不自动覆盖他人的更新。检查所有现存完成接诊入口，确保不能绕过病历和审计直接将预约更新为完成。

### 页面和接口

- 扩展现有 `GET /medical-records/doctor?appointmentId=...`，医生可读取属于自己的草稿和正式病历及其医嘱；不允许医生访问其他医生记录。
- 新增 `POST /medical-records/draft`，要求医生会话、CSRF Token、预约编号和适用的草稿版本；在服务端校验归属、预约状态、字段上限与医嘱内容。响应返回草稿编号、状态与新版本。
- 保留 `POST /medical-records/finalize`，扩展处理草稿版本与必填校验，同时继续支持没有草稿的合法直接提交。
- `doctor-schedule/encounter.html` 增加“保存草稿”并自动恢复已有草稿；“保存草稿”和“完成接诊”分别处理校验，前者不因正式提交必填项为空而被浏览器阻止。保存、完成、版本冲突及服务端错误均显示明确提示。
- `GET /medical-records/patient` 的列表和详情只返回本人 `FINAL` 记录及对应医嘱。未登录、角色错误和资源不可访问分别按项目既有的 401、403、404/403 约定处理，不泄露是否存在其他人的记录。
- 新增草稿写接口纳入现有认证和 CSRF 过滤，并测试过滤器实际执行顺序；不要仅依赖页面按钮隐藏。

## 二、管理员审计查询

保留现有 `GET /audit-logs?limit=...` 的调用兼容性。增加管理员专用的分页查询能力，提供时间范围、角色、操作人 ID、动作和结果筛选；筛选条件可组合，使用参数化 SQL、合理的分页上限和稳定排序（时间及日志主键倒序）。页面提供筛选、清空、分页、无结果与加载失败提示。时间范围、枚举和页码非法时返回清晰的 400，避免无界查询。

管理员认证在服务端执行：未登录返回 401，患者和医生返回 403；不能仅通过隐藏页面控制。查询出错返回明确服务错误，不伪装成空列表。沿用只读追加的审计数据模型，不提供日志修改、删除接口。页面对输出内容转义，仅显示必要元数据，不显示密码、哈希、令牌、身份证号、完整病历或医嘱正文。根据实际查询条件和执行计划添加必要索引，避免无依据地添加大量索引。

## 三、审计完整性与故障策略

### 范围与成功事件

梳理实际可用的登录、退出、排班新增/修改/删除、预约/取消/改期、开始接诊、草稿保存、完成接诊、改密及管理员敏感操作入口，形成入口与事件映射，避免旧路径绕过或重复记账。日志至少包含服务端确认的角色、操作人、动作、目标类型及编号、结果、请求方式、路径、来源地址和时间；目标编号来自业务执行结果，例如数据库返回的新预约主键，而非信任请求或使用 `MAX(id)`。

对于以上涉及数据库状态变化且由项目事务控制的关键成功操作，业务变更和成功审计共用同一个 MyBatis `SqlSession` 和同一个事务；审计写入失败时整体回滚并返回明确错误（fail-closed）。如改期产生新旧预约，在不记录敏感业务正文的前提下保证可关联；病历正式提交与对应预约完成事件必须可追踪到实际预约。消除原有过滤器对这些成功事件的重复记账，同时保留失败事件处理。

登录、退出等 Session 操作以及无法与业务数据放入同一数据库事务的情况，分别设计和说明日志与会话变化的顺序及故障行为，不声称它们天然满足数据库事务原子性。检查密码兼容升级、改密及管理员操作的实际调用链，符合上述事务条件的数据库更改使用同一事务；无此条件的路径明确报告实际保证与限制。

### 失败事件与可用性

认证失败、权限拒绝、CSRF 拒绝和业务校验失败使用独立、脱敏的失败事件记录，避免随业务回滚消失。明确覆盖过滤器执行顺序、未捕获异常、响应状态与业务返回失败；异常不能因响应默认为 200 被误记为成功。失败日志写入也可能因数据库故障失败：此时不能承诺数据库里必有该失败记录，必须产生不含敏感数据的服务器侧告警/错误日志，并在交付中说明此边界。

审计记录严禁写入请求参数原文、密码、密码哈希、CSRF Token、身份证号、完整病历或医嘱内容。对其他目标信息采用白名单，保证日志仅包含必要的元数据。审计不可用时拒绝提交关键数据库业务变更，是可追踪性优先于业务可用性的已确认取舍。

## 四、兼容迁移与发布

- 新建独立增量迁移，不修改已经执行的旧迁移，也不删除表、记录或现有字段。脚本兼容用户的 MySQL 8.0.19；不要使用该版本不支持的 `ADD COLUMN IF NOT EXISTS`，使用 `information_schema` 进行必要的存在性检查，并提供重复执行验证。
- 先检查库名、版本、字段、索引和历史数据，评估是否有不符合新增约束的数据。历史病历保持正式状态，不要求补填历史诊疗方案；新增提交使用新必填规则。
- MySQL DDL 可能隐式提交，迁移不能假称整体事务回滚。发布前提供备份建议、分步骤校验、失败后恢复/回退方案。特别说明产生空诊断草稿后不能直接恢复旧的 `NOT NULL` 约束，必须先处理草稿并经用户确认；不要静默丢弃数据。
- 改动先在隔离测试数据库验证，不对现有数据库执行迁移、清库或改写数据，不覆盖现有 WAR 或重启 Tomcat；后续部署须按用户授权和明确的备份、迁移、回退流程进行。

## 五、验收标准

1. 医生为自己的 `IN_PROGRESS` 预约保存未填完的草稿，刷新后内容、医嘱和版本可恢复；预约仍为 `IN_PROGRESS`，患者不可见。
2. 空诊断或空诊疗方案不能完成接诊；填写必填项后，病历为 `FINAL`、预约为 `COMPLETED`，医患双方状态及患者可见内容一致。旧的直接完成路径不能绕开这一规则。
3. 不同医生、患者以及不同患者之间均不能跨身份读写；`FINAL` 不可被静默覆盖；多窗口陈旧版本得到 409，未提交输入不被清空。
4. 管理员能够按时间、角色、操作人、动作和结果单独及组合筛选并分页；无结果与查询异常可区分。未登录、患者和医生无法查看审计接口或页面。
5. 对预约、排班、病历和可纳入数据库事务的其他关键写操作注入审计插入失败，确认业务和成功日志均回滚；成功路径恰有对应日志且含正确目标编号。拒绝/失败路径产生失败审计或在日志库故障时产生安全的服务器告警，不报告虚假成功。
6. 覆盖 CSRF、越权、异常、并发、历史数据兼容、日志脱敏与迁移重复执行；运行现有全部测试和新增测试，必要时在 MySQL 8.0.19 隔离库执行真实事务及迁移测试。未运行的项目如实标注。
7. 交付修改文件、迁移 SQL、API、状态与权限说明、测试结果、人工验收步骤和已知限制。若未进行真实数据库测试或部署，不得声称已通过完整验收或已部署。
