## 3. 排班修改与撤销

现有实现发现任何预约历史就拒绝修改，更新时又会删除并重建三个时段。取消和改期历史仍引用这些时段，因此不能简单放开检查。

- 严格解析排班日期，拒绝不存在的日期。新建、移动及新增开放号源仅限今天及以后；不追溯修改过去排班。
- 修改同一天的排班时，逐时段检查：BOOKED、IN_PROGRESS、COMPLETED 的预约所占时段保持不变；其余时段可以开放或关闭。取消和改期历史不阻止调整，但原时段主键必须保留。
- 有任何预约历史的排班不允许整体移动到其他日期。完全没有历史引用、没有占用的未来排班才允许改日期。
- 完全没有预约历史的未来排班可以物理删除；存在历史但没有待接诊或接诊中预约时，将“删除”解释为撤销未来开放号源，保留排班和时段行，并明确提示“排班已撤销，历史记录保留”。页面标明已关闭状态，避免误以为仍可预约。
- 存在 BOOKED 或 IN_PROGRESS 时拒绝整日撤销，提示先处理有效预约；本次不自动取消患者预约。
- 事务内锁定并检查时段，条件更新号源，避免预约与撤班并发时留下失效关联。重复撤销应有明确结果。
- 页面说明哪些时段不能修改；非法日期返回 400，归属越权返回 403，业务占用冲突返回 409。

涉及 `DatesServiceImpl`、`DatesMapper`、`ScheduleSlotsMapper`、预约关联查询及医生排班页。预约取消不退款等其他规则保持不变。

## 4. 管理员基础数据维护

- 医生、患者、科室、职称列表增加服务端关键字筛选、分页和稳定排序，默认每页 10 条，每页上限 100 条。关键字长度上限 100，SQL 使用参数绑定，按文字处理通配符。
- 保留 `items` 列表字段，补充 `pageNum`、`pageSize`、`total`、`pages` 元数据；新版页面同步使用分页，不靠浏览器加载全表后过滤。
- 医生科室、职称和新增科室的上级科室改为名称下拉选择。选项接口与分页列表分开，完整加载选项，不误用第一页充当所有选项；选项按需限制字段，仍只允许管理员读取。
- 修复科室说明 `departmentDiscription` / `departmentDescription` 的回填不一致，保留现有 JSON 拼写兼容，避免编辑时清空说明。
- 管理员新增患者与公开注册采用相同的姓名、身份证、电话、邮箱和密码规则；修复可选字段长度未实际检查的问题。医生入职日期严格解析，检查科室、职称存在性。
- 姓名、联系方式、说明等允许字段在服务端校验；继续禁止通过患者编辑表单修改身份或余额。错误提示指出具体字段，保留失败时的输入；保存成功保留操作结果提示。
- 不增加账户体系或科室层级整体迁移功能。新增科室继续自动计算层级和路径，已有科室本次只修改名称、说明。

## 5. 基础数据删除

- 医生删除检查日期排班、时段、预约、病历及实际存在的旧业务引用；患者删除检查预约、病历、余额流水及实际存在的旧业务引用。
- 患者余额非零一律拒绝删除，返回 409；历史迁移账号可能没有余额流水，不能以“无流水”推断余额为零。事务内锁定患者行检查余额，不自动清零或退款。
- 科室删除检查下级科室和医生；职称删除检查医生引用。
- 有关联数据返回 `HAS_REFERENCES` / HTTP 409，并说明是预约、排班、病历或资金历史等哪类原因。不存在对象返回 404，不能用笼统 500 代替正常业务冲突。
- 仅无引用对象才物理删除。保留数据库外键作为最后保障，处理检查后并发产生关联的情况；不级联删除业务历史，不因删除账号删除审计记录。
- 每次成功删除与审计写入同一事务；拒绝删除记录失败审计。页面先确认再提交，失败后保持当前筛选和页码，成功后处理当前页变空。
- 不以本次“完善删除”为由新增软删除字段、自动停用、清空余额或删除历史记录。

## 6. 病历与医嘱使用体验

- 患者病历列表增加预约日期范围、医生筛选和服务端分页；显示医生姓名、预约日期/时段、定稿时间以及医嘱。始终只查当前登录患者的 FINAL 记录，不能由前端患者编号决定查询范围。
- 新列表读取入口单独使用分页响应，保留现有单条病历入口及旧列表响应兼容，避免其他页面被接口形状变化破坏。
- 在一页病历查询之后批量读取这些病历的医嘱，避免每条记录额外执行一次查询；空列表不生成空 IN SQL。
- 医生填写页增加未保存修改提醒，新增和删除医嘱也计入修改状态；保存成功后清除提醒，保存失败继续提醒。保存中阻止重复提交，不将病历正文写入 localStorage。
- 显示草稿最近保存状态。版本冲突保留当前输入并提示重新核对，不自动覆盖另一窗口的内容；正式提交前提供确认。
- 保留手动保存方式，本次不增加自动保存，避免未经确认改变版本冲突处理。继续执行定稿必填规则、医嘱最多 20 项和正式病历不可覆盖规则。
- 补齐空结果、加载失败、权限失效、分页边界和小屏显示。

## 7. Docker 部署与运维

- 数据库继续使用 OceanBase；依据本机现有镜像版本和实际验证结果固定镜像版本或摘要，不自动升级现有数据卷。
- 应用增加独立持久化上传目录，通过配置指定目录并挂载数据卷；提供稳定的头像访问路径。已存在的部署目录头像提供一次性复制步骤，不能靠重建容器迁移旧头像。
- 增加应用就绪检查：数据库可访问且应用已启动返回 200，否则 503，仅输出状态，不输出连接串、密码或业务数据。Compose 使用该检查并配置重启策略。
- 保留源码构建流程，另提供无需构建即可启动的镜像部署配置，通过 `HOSPITAL_APP_IMAGE` 明确指定已发布镜像。现有 `v1.0.1-lsy-chl` 不视为包含本次修改，本次更新的发布镜像标签留给用户确定，不自动上传或覆盖 Docker Hub 标签。
- 文档提供源码启动、镜像启动、配置业务数据库账号、健康检查、日志查看、保留数据卷更新及停止流程。数据库初始化明确区分空库和已有数据，不能自动导入演示数据。
- 增加本地备份及恢复说明/脚本：凭据通过环境或安全输入传递，输出排除版本控制。恢复必须显式指定目标并检查，不能默认覆盖当前真实业务库。
- 不执行 `down -v`、清空数据库、删除卷或重新迁移 MySQL。运行容器验证前确认本地环境与测试环境独立，避免占用 8080 端口或误连真实业务库。

当前环境检查：Docker CLI 已安装，但 Docker Desktop Linux Engine 管道不可连接。实现和离线检查可继续，容器级验证需 Docker 启动后执行；未实际执行的检查不能标为通过。
